## 1. System Overview

ContextGraph is a **DAG-based context management system** for LLM assistants, replacing the standard temporal sliding window with three retrieval layers:

1. **Sticky layer** (~30% budget) — pinned messages, active tool chains
2. **Recency layer** (~25% budget) — most recent messages regardless of topic  
3. **Topic layer** (~50% budget) — semantically relevant messages retrieved by inferred tags

**Architecture:**
```
Incoming message → strip_envelope → extract_features → EnsembleTagger → MessageStore (SQLite)
                                                                              ↓
Retrieval query → tag inference → sticky/recency/topic assembly → token-budgeted context window
```

**Components:**
- **Python FastAPI server** (`api/server.py`, port 8302) — ingest, assemble, tagging, Current Thing, dashboard
- **OpenClaw plugin** (`plugin/index.ts` → `dist/index.js`) — bridges OpenClaw ContextEngine interface to Python API
- **SQLite store** (`~/.tag-context/store.db`) — 6,187 messages (as of audit), WAL mode
- **Goal watcher thread** — async LLM calls to qwen3-coder:30b on Mac Studio (172.23.1.31:11434) for goal-drift detection

**Channel label distribution** (from DB):
| Channel | Messages |
|---------|----------|
| garrett | 5,180 |
| rich    | 914 |
| jeremy  | 1 |

**Graph mode state** (`~/.tag-context/graph-mode.json`):
- rich: **OFF**, garrett: **OFF**, umair: **ON**, gateway-client: OFF

**Production results** (from SPEC.md): 11.8% token savings, 23.6 msgs/query, 14.6 topic-retrieved msgs/query, 99%+ cache hit rate at 4K budget (March 2026 baseline).

## 2. Strengths

### S1: Solid cross-user isolation
Channel-label scoping is consistently threaded through all retrieval paths. NULL channel_label rows (verified: **0 in current DB**) cannot leak to user-scoped queries because SQL `WHERE channel_label = ?` correctly excludes NULLs.

### S2: Robust ingest-time sanitization
Multiple defense layers:
- **Reasoning block stripping** (`store.py:240-255`): `[[reasoning]]…[[/reasoning]]` and `<thinking>…</thinking>` blocks are stripped before persistence. Verified **0 contaminated rows** post-May-8.
- **Envelope stripping** (`utils/text.py`): 15+ regex patterns strip OpenClaw metadata envelopes, runtime context, subagent preambles, inter-session messages. Verified **0 envelope-contaminated rows** in current DB.
- **Injection pattern sanitization** (`api/server.py:251-270`): prompt injection patterns are `[REDACTED]` at ingest time.
- **Boilerplate rejection** (`api/server.py:290`): `[metadata-only message]` and empty content are skipped.
- **Automated turn detection** (`logger.py:54-120`): cron, heartbeat, watcher, subagent events are tagged `is_automated=1` and excluded from retrieval.

### S3: Well-designed pane-exclusion (Jun 9 work)
The Jun 9 pane-exclusion changes are **complete and correct**:
- `assembler.py` diff (2 changes): user-scope recency and topic layers now pass `exclude_dashboard=True`, preventing dashboard pane content from leaking into main-channel assembly.
- `store.py` diff (2 changes): `get_recent_by_channel()` and `get_by_tag_scoped()` accept `exclude_dashboard` parameter, filtering `session_id NOT LIKE '%:dashboard:%'`.
- Design intent is sound: pane work stays pane-scoped; cross-scope access goes through explicit bridging (Current Thing).

### S4: Graceful degradation
- Python API unreachable → plugin falls back to pass-through (vanilla linear window)
- Goal watcher LLM failures → marks status "offline" after 5 consecutive failures, keeps last-known goals
- Oversized messages → summarization or skip; never blow the budget
- Unknown scope values → coerced to 'global' for forward compatibility

## 3. Weaknesses & Gaps

### P0 — Data Integrity / Cross-User

#### W1: SUBAGENT CONTEXT INJECTION — No session-type gating
**Severity: P0 (when graph mode is ON)**  
**Affected users: umair (currently), any future user who enables graph mode**

**Evidence:**
- Gateway log shows subagent sessions with `ownsCompaction=true` for users with graph mode ON:
  ```
  2026-06-10T09:30:18.759 [PANE-DIAG] attempt sessionKey=agent:jarvis-umair:subagent:5f01b667-... 
    ce=true ownsCompaction=true ... branch=loop-hook
  ```
- The `inferChannelLabel` regex (`/^agent:[^-]+-([^:]+):/`) extracts "rich" from `agent:jarvis-rich:subagent:<uuid>` — treating subagent sessions identically to direct sessions.
- `inferSubchannelLabel` returns `null` for subagent sessions (`:subagent:` is not a known surface type and doesn't match `:dashboard:`), so scope falls to `'user'`.
- Python server assemble log confirms: `[assemble] scope=user sid=...040f1b4c-a55 ch=rich`
- With the **installed** plugin's model-aware budget formula: `min(120K, max(32K, floor(tokenBudget * 0.25)))`, a 200K-window model (Opus/Sonnet) gets a **50,000-token retrieval budget** injected into every subagent session.
- This retrieves the user's entire conversation history (all dashboard panes + direct channel content) and prepends it to the subagent's narrow task context.
- **Observed impact**: Rich reported ~175K token context in failed subagent runs vs ~34K clean. This is the mechanism.

**Root cause:** The plugin has no concept of session types. All sessions matching `agent:<X>-<user>:` are treated identically — the same graph-mode gate, the same budget, the same retrieval scope.

**Fix sketch (est. 2-4h):**
1. Add `isSubagentSession(sessionKey)` check (match `:subagent:` segment)
2. In `ownsCompactionForSession()`: return `false` for subagent sessions
3. In `assemble()`: early-return pass-through for subagent sessions
4. Alternatively: add to `graph-mode.json` a `subagent_injection: false` toggle per user

#### W2: Current Thing snapshot orphans for subagent sessions
**Severity: P1**  
**Affected: all users with graph mode ON**

**Evidence:**
```sql
-- 12 of 31 snapshots are ephemeral subagent UUIDs
SELECT COUNT(*) FROM current_thing_snapshots WHERE session_id LIKE '%:subagent:%';
-- 12
-- 262 history entries for those subagents
SELECT COUNT(*) FROM current_thing_history WHERE session_id LIKE '%:subagent:%';
-- 262
```

Each subagent gets a unique UUID that is never reused. Snapshots and history accumulate forever without cleanup.

**Fix sketch (est. 1h):** Add a GC pass (e.g., daily cron or startup hook) that deletes snapshot + history rows for session_ids matching `:subagent:` older than 24h.

#### W4: Current Thing GET endpoint missing auth
**Severity: P1**  
**Affected: any user with network access to Multigraph server**

**Evidence** (`server/index.js:1214`):
```javascript
// GET has NO requireUser — open to any client
app.get('/api/multigraph/current-thing/:paneId', async (req, res) => { ... })

// POST endpoints correctly use requireUser
app.post('/api/multigraph/current-thing/:paneId/update', requireUser, ...)

```

Any client on the network can read any pane's Current Thing snapshot (including goals, identity, skills). Writes are correctly gated.

**Fix sketch (est. 15min):** Add `requireUser` middleware to the GET endpoint.

#### W5: Frontend CurrentThingPill response unwrapping bug
**Severity: P1 (Current Thing pill never shows data)**  
**Affected: all Multigraph dashboard users**

**Evidence chain:**
1. Python `/current-thing` returns `{"snapshot": {...}, "rendered": "..."}` (`server.py:601-604`)
2. Multigraph proxy forwards raw response: `res.json(data)` (`server/index.js:1221-1222`)
3. Frontend sets entire response as state: `setSnapshot(data)` (`CurrentThingPill.tsx:125`)
4. Frontend accesses `snapshot.goals`, `snapshot.identity`, etc. (`CurrentThingPill.tsx:256-331`)
5. But `data.goals` is `undefined` — goals are at `data.snapshot.goals`!

The `CTSnapshot` interface expects flat fields (`goals`, `identity`, etc.) but the API response wraps them under `.snapshot`. The pill silently renders nothing because optional chaining (`snapshot?.goals?.primary`) returns `undefined`.

**Fix sketch (est. 15min):** Either:
- Frontend: unwrap `const snap = data.snapshot ?? data` in fetchSnapshot
- Or server proxy: `res.json(data.snapshot)` to unwrap before forwarding

#### W7: Goal watcher "database is locked" errors
**Severity: P1**  
**Affected: umair (or any user with Current Thing ON)**

**Evidence** (`~/Library/Logs/contextgraph.err.log`):
```
[goal_watcher] Unexpected error: OperationalError('database is locked')
```

Despite WAL mode and `busy_timeout=30000`, the goal watcher thread encounters lock contention with the main MessageStore. This can lose goal updates and trigger restarts (the plist's KeepAlive restarts the process).

**Fix sketch (est. 2h):** 
- Use a dedicated SQLite connection for the watcher thread with increased retry
- Or move to connection pooling with proper retry backoff
- Or separate Current Thing tables into their own DB file

#### W8: Residual boilerplate in historical data
**Severity: P1 (data quality)**

**Evidence:**
```sql
-- 16 multigraph:restore boilerplate messages (all pre-May 7)
SELECT COUNT(*) FROM messages WHERE user_text LIKE '%multigraph:restore%';
-- 16

-- 6 pre-compaction memory flush instructions stored as conversation
SELECT COUNT(*) FROM messages WHERE user_text LIKE '%SOUL.md%';

These are from before the envelope stripping and boilerplate rejection were comprehensive. They are tagged, scored, and retrieved as normal messages — polluting topic retrieval with system instructions.

```

### P2 — Polish / Efficiency

#### W9: Token budget escalation path lacks caps for small-model subagents
**Severity: P2**

The installed plugin uses `GRAPH_TOKEN_BUDGET_FLOOR = 32000`. Even for small Sonnet sub-tasks that could run with 4K of graph context, the floor guarantees 32K retrieval + 10 recent messages. This is generous for subagents that typically run a single narrow task.

(Partially addressed by W1 fix — excluding subagents entirely is the right answer.)

#### W10: No automated regression tests for plugin → installed sync
**Severity: P2**

No CI/CD, no file watcher, no startup hash check. The May 7 cross-user bleed was caused by the same plugin staleness pattern. It will happen again.

**Fix sketch (est. 2h):** Add a startup hash check in the plugin's `register()`:
```typescript
// Compare hash of this file against source dist; warn if mismatched
const sourceHash = crypto.createHash('md5').update(fs.readFileSync(sourceDistPath)).digest('hex');
const installedHash = crypto.createHash('md5').update(fs.readFileSync(__filename)).digest('hex');
if (sourceHash !== installedHash) {
  logger.warn(`contextgraph: INSTALLED DIST DIFFERS FROM SOURCE — rebuild and redeploy!`);
}
```

#### W11: Double assemble calls visible in gateway log
**Severity: P2**

**Evidence** (gateway log):
```
10:15:10.501 contextgraph assemble: 11 msgs, ~0 tok
10:15:10.541 contextgraph assemble: 11 msgs, ~0 tok
```

Two assemble calls 40ms apart for the same turn. This is likely the `ownsCompactionForSession` check + actual assemble, or a retry. Harmless but doubles API load.

#### W12: `Pre-compaction memory flush` not caught by automated-turn detector
**Severity: P2**

`_is_automated_turn()` in `logger.py` does not match "Pre-compaction memory flush" — these system-generated messages are stored as non-automated content. Only affects historical data (6 rows), but the pattern should be added for future-proofing.
